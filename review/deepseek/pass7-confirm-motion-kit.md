1. `lib/ui/zed/zed_motion.dart` — `_ZedPageTransitionState.didUpdateWidget` (exit creation): the exit entry is created with `top.forward`, so a reversed navigation reuses the page’s original direction. Scenario: navigate A→B (`B.forward == true`), then go back B→A (`widget.forward == false`). B is made an exit with `forward == true`, so for `slide` B exits left while A enters from the left. If B is caught mid-entrance at `progress == 0.5`, its slide offset jumps from `+width/6` on the entrance transform to `-width/6` on the exit transform. This contradicts the comment that a mid-entrance page “leaves from the matching visual state instead of snapping”.

2. `lib/ui/zed/zed_motion.dart` — `_ZedPageTransitionState.didUpdateWidget` (`progress` seeding): `progress = top.controller.value.clamp(0.0, 1.0)` clamps spring overshoot. Scenario: `ZedTransition.elastic` entrance overshoots to `controller.value > 1`; if the user navigates away then, `progress` becomes `1`, the exit controller starts at `0`, and the page snaps from the overshoot transform (`scale > 1`, negative offset) to the fully settled state before exiting. This also contradicts the “matching visual state” comment.

3. `lib/ui/zed/zed_kit.dart` — `_GlassTabBarState.didChangeDependencies` / `_shrinkListener`: when the primary controller initially has zero positions, `_lastSeen` remains `0` and `_shrinkAnchorStale` stays `false`, because the code only sets `_lastSeen` when `positions.length == 1` and has no `else` branch to set stale. Scenario: the tab bar mounts before the scroll position attaches; the scroll view later restores to offset `500`. The first scroll event computes `d = 500 - 0`, immediately making `_downAccum > 48` and shrinking the bar, even for a tiny scroll. An upward scroll can likewise be misread as downward.

4. `lib/ui/zed/zed_motion.dart` — `_ZedEntranceState.initState`: the window is reset whenever the gap since the last entrance exceeds 800 ms: `last != null && now.difference(last) > 800`. Scenario: a server list mounts, then after >800 ms the user scrolls and a lazy item builds for the first time. That late item resets `windowStart` and runs the entrance spring, although the class doc says the entrance is active only within the 800 ms window from the list’s first build. The result is rows animating in during later scrolling.
