1. `lib/ui/zed/zed_motion.dart` — `_ZedPageTransitionState._transform`, reduce-motion branch: `rawT` is passed directly into `Opacity(opacity: entering ? rawT : 1 - rawT)`. Elastic entrances use an unbounded spring controller and can overshoot above 1; springy exits are seeded with `1 - raw`, which can be negative. If `reduceMotion` is toggled on while such a controller is active, `Opacity` receives an opacity outside `[0,1]` and asserts (or renders invalid opacity). Evidence: the reduce-motion branch returns `Opacity(opacity: entering ? rawT : 1 - rawT, child: child)` without clamping, while `didUpdateWidget` deliberately seeds `exit.controller.value = springy ? 1 - raw : ...`.

2. `lib/ui/zed/zed_motion.dart` — `_ZedPageTransitionState.didUpdateWidget`, non-spring exit path: the exit duration is scaled twice. For an entrance caught at progress `p`, the code sets `exitDuration = spec.duration * p`, sets that as `controller.duration`, and calls `forward()`. `AnimationController.forward()` additionally scales duration by the remaining fraction to the target, so the actual exit duration becomes `spec.duration * p * p`. Example: `p = 0.5` exits in roughly one quarter of the intended exit duration, not half. Evidence: `exitDuration = Duration(milliseconds: math.max(1, (spec.duration.inMilliseconds * progress).round()))`, then `exit.controller.duration = exitDuration; exit.controller.forward()`.

3. `lib/ui/zed/zed_motion.dart` — `_ZedPageTransitionState.didUpdateWidget` + `_transform`, elastic exit: a springy entrance caught mid-overshoot has `raw > 1`, and the exit controller is seeded with `1 - raw` (negative) to preserve the overshoot. But `_transform` later clamps every non-entering style with `rawT.clamp(0.0, 1.0)`, so that negative seed becomes `0` and the outgoing page snaps to fully present instead of continuing from the overshot visual state. Evidence: `exit.controller.value = springy ? 1 - raw : ...` and `final t = entering && widget.style == ZedTransition.elastic ? rawT : rawT.clamp(0.0, 1.0);`. This contradicts the comment saying the unclamped seed is needed or the exit snaps.

4. `lib/ui/zed/zed_kit.dart` — `ScrollDirectionTracker._attach/_onScroll` and `_GlassTabBarState._shrinkListener`: the stale-anchor flags are only set when a scroll event fires while the shared `PrimaryScrollController` has multiple positions, or when `didChangeDependencies` runs. If a page transition attaches a second scroll position and then detaches it with no scroll event during that interval, `positions.length` returns to 1 while `_anchorStale` / `_shrinkAnchorStale` remains false. The next scroll on a new page with a different saved offset compares against the old page’s `_lastOffset` / `_lastSeen`, so a small upward scroll can be misread as a large down-scroll, hiding the Bento dock or shrinking the Glass tab bar. Evidence: `_anchorStale` is only set inside `if (controller.positions.length != 1)` in `_onScroll`, and `_shrinkAnchorStale` similarly only inside `if (c.positions.length != 1)`.

5. `lib/ui/zed/zed_motion.dart` — `_ZedEntranceState`: `widget.enabled` is read only in `initState`; there is no `didUpdateWidget`. If the parent rebuilds the same mounted `ZedEntrance` with `enabled` changed, the state does not react. `true -> false` leaves the timer/controller running and keeps `mountedCount` incremented until dispose; `false -> true` leaves `_animate` false and the entrance never creates a controller or joins the mount group. Evidence: `if (!widget.enabled) return;` and all animation setup happen only in `initState`.

6. `lib/ui/zed/zed_motion.dart` — `_ZedPressScaleState` Listener handlers: there is no pointer-count tracking. If two pointers press the child, the first `onPointerUp` calls `_to(1)` and springs the scale back to rest even though another pointer is still down. Evidence: `onPointerUp: (_) => _to(1)` and `onPointerCancel: (_) => _to(1)` run unconditionally for any pointer event.
